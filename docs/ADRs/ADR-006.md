# ADR-006 - Guards de rota para controle de acesso

- Status: proposto
- Decisores: Heloísa Tognólli Scarante
- Data: 2026-09-18

## Contexto e Declaração do Problema

O frontend da Escola de TI precisa aplicar regras de acesso diferentes por funcionalidade: o **teste vocacional** exige que o usuário esteja logado, e os **simulados** exigem uma assinatura ativa. Como o frontend é uma SPA em Vite + React ([ADR-001](ADR-001.md)), a navegação acontece no próprio navegador e o usuário pode acessar qualquer rota digitando a URL diretamente, então essas regras precisam ser aplicadas de forma consistente na camada de rotas.

Como o frontend deve aplicar as regras "teste vocacional exige login" e "simulados exige assinatura" sem duplicar essa verificação em cada tela?

## Fatores da Decisão

- Centralização: as regras de acesso devem ficar em um único lugar, e não espalhadas pelas telas;
- Reuso e composição: novas rotas protegidas devem ser fáceis de declarar, combinando as regras (ex.: simulados exigem login **e** assinatura);
- Experiência do usuário: quem não atende à regra deve ser redirecionado para o passo certo (login ou assinatura), sem ver conteúdo protegido nem uma tela em branco;
- Segurança: a regra no frontend melhora a experiência, mas não protege os dados, então a autorização real precisa continuar no backend Spring Boot;
- Consistência com a stack: a solução deve funcionar bem com a SPA em React e com o estado de servidor gerenciado pelo React Query ([ADR-003](ADR-003.md));
- Proteção da sessão: o token de autenticação não deve ficar acessível ao JavaScript da página, reduzindo o impacto de um ataque XSS.

## Opções Consideradas

- Opção 1: Guards de rota centralizados com React Router, como rotas de layout que envolvem as rotas protegidas (`RequireAuth` e `RequireSubscription`), com validação final no backend
- Opção 2: Verificação dentro de cada página ou componente
- Opção 3: Depender apenas do backend, tratando as respostas 401/403 no frontend

## Resultado da Decisão

Opção escolhida: "Opção 1 - Guards de rota centralizados com React Router", porque concentra as regras de acesso na definição das rotas, permite combinar as regras de forma declarativa (teste vocacional com `RequireAuth`; simulados com `RequireAuth` + `RequireSubscription`) e garante o redirecionamento correto sem que a tela protegida chegue a ser renderizada. A autorização continua sendo validada pelo backend em cada requisição, e o guard no frontend serve como camada de experiência de uso.

### Detalhes da implementação

- **Biblioteca de rotas:** React Router, por ser o padrão de mercado para SPAs em Vite + React e ter ampla disponibilidade de conteúdo. Os guards são rotas de layout que renderizam `<Outlet />` quando o acesso é permitido ou `<Navigate />` quando não é. O aninhamento faz a composição das regras: a rota de simulados fica dentro de `RequireAuth` e de `RequireSubscription`.
- **Fonte do estado de login e assinatura:** o frontend não deduz esse estado sozinho. Ele consulta um endpoint `GET /me` do backend, consumido com `useQuery` ([ADR-003](ADR-003.md)), que retorna o usuário e o status da assinatura.
- **Armazenamento da sessão:** o token de autenticação fica em cookie `HttpOnly` (com `Secure` e `SameSite`), definido pelo backend, e não em `localStorage`. Assim o JavaScript da página não consegue ler o token. As requisições do frontend enviam o cookie (`credentials: "include"` ou `withCredentials`).
- **Backend:** o Spring Security valida login e assinatura em todos os endpoints protegidos, com CORS configurado para a origem do frontend com credenciais habilitadas e proteção contra CSRF, já que a autenticação passa a ser feita por cookie.
- **Conteúdo protegido:** as questões dos simulados e demais conteúdos restritos não podem estar no bundle do frontend, que é público. Eles são entregues apenas pela API, que responde `401` (não autenticado) ou `403` (sem assinatura) quando o acesso não é permitido.
- **Tratamento global de 401/403:** um tratamento central (ex.: `QueryCache` do React Query ou interceptor HTTP) redireciona o usuário quando o backend nega o acesso, cobrindo o caso de a sessão ou a assinatura expirarem com o app aberto.

Comportamento esperado dos guards:

| Situação do usuário | Teste vocacional | Simulados |
| --- | --- | --- |
| Não logado | Redireciona para o login | Redireciona para o login |
| Logado, sem assinatura ativa | Acesso liberado | Redireciona para a página de assinatura |
| Logado, com assinatura ativa | Acesso liberado | Acesso liberado |

Após o login, o usuário deve ser levado de volta à rota que tentou acessar.

### Consequências Positivas

- Regras de acesso em um único lugar, fáceis de auditar e de alterar;
- Novas rotas protegidas são declaradas apenas envolvendo-as com o guard adequado;
- Telas protegidas não são renderizadas para quem não tem permissão, evitando exibir conteúdo indevido ou disparar requisições desnecessárias;
- Os guards podem reaproveitar os dados de sessão e assinatura já gerenciados pelo React Query, sem criar um novo mecanismo de estado;
- O token em cookie `HttpOnly` não pode ser lido por scripts, o que reduz o risco de roubo de sessão em caso de XSS;
- O React Router é uma biblioteca consolidada, com ampla documentação e exemplos para esse padrão de guards.

### Consequências Negativas

- O guard no frontend não é uma barreira de segurança, pois o código do cliente pode ser contornado; o backend precisa validar login e assinatura em todos os endpoints protegidos;
- É preciso tratar o estado de carregamento da sessão e da assinatura antes de decidir o redirecionamento, para não expulsar o usuário logado por engano nem exibir uma tela em branco;
- Se a assinatura expirar durante o uso, o frontend pode estar desatualizado até a próxima verificação, e as respostas 401/403 do backend também precisam ser tratadas;
- A lista de rotas protegidas e suas regras precisa ser mantida atualizada conforme o sistema cresce;
- O uso de cookie exige configurar CORS com credenciais e proteção contra CSRF no backend, além de cuidar dos atributos `Secure` e `SameSite`, o que aumenta a complexidade em relação a enviar um token no cabeçalho;
- O frontend não consegue ler o token, então o estado de login depende sempre de consultar o backend (`GET /me`), e não de decodificar o token no cliente;
- Adiciona uma dependência externa ao projeto (React Router).

## Prós e Contras das Opções

### Opção 1 - Guards de rota centralizados com React Router

Rotas de layout do React Router que envolvem as rotas protegidas, verificam login e assinatura e redirecionam quando a regra não é atendida, com o backend validando o acesso em cada requisição.

- Bom, porque centraliza as regras de acesso em um único lugar;
- Bom, porque permite combinar regras de forma declarativa (login + assinatura);
- Bom, porque evita renderizar telas protegidas para quem não tem acesso;
- Bom, porque facilita a criação de novas rotas protegidas;
- Ruim, porque exige tratar o estado de carregamento da sessão antes do redirecionamento;
- Ruim, porque não substitui a validação no backend.

### Opção 2 - Verificação dentro de cada página ou componente

Cada tela consulta o estado de login e assinatura e decide se exibe o conteúdo ou redireciona.

- Bom, porque não exige nenhuma estrutura adicional na camada de rotas;
- Bom, porque permite regras muito específicas por tela;
- Ruim, porque repete a mesma lógica em várias telas;
- Ruim, porque esquecer a verificação em uma tela deixa a rota desprotegida;
- Ruim, porque a tela pode ser montada (e disparar requisições) antes de a verificação terminar.

### Opção 3 - Depender apenas do backend

O frontend não aplica regras de acesso e apenas reage às respostas 401/403 da API, redirecionando o usuário.

- Bom, porque a regra fica em um único lugar, o backend, que é a fonte da verdade;
- Bom, porque não há risco de o frontend divergir do backend;
- Ruim, porque a tela protegida é carregada e a requisição é feita antes de o usuário ser redirecionado;
- Ruim, porque a experiência é pior: o usuário só descobre que não tem acesso depois de uma tentativa que falhou;
- Ruim, porque não trata as regras de login e de assinatura de forma distinta e preventiva na navegação.

### Armazenamento da sessão: cookie `HttpOnly` (escolhido) vs `localStorage`

Complementa a decisão dos guards, definindo onde o token de autenticação fica guardado no navegador.

**Cookie `HttpOnly`**

- Bom, porque o JavaScript da página não consegue ler o token, o que limita o dano de um ataque XSS;
- Bom, porque o navegador envia o cookie automaticamente nas requisições, sem código extra no frontend;
- Ruim, porque exige CORS com credenciais e proteção contra CSRF no backend;
- Ruim, porque o frontend não lê o token e depende do `GET /me` para saber quem está logado.

**`localStorage`**

- Bom, porque é simples de implementar e de enviar o token no cabeçalho `Authorization`;
- Bom, porque não exige tratamento de CSRF;
- Ruim, porque qualquer script executado na página (XSS) consegue ler e roubar o token;
- Ruim, porque o token persiste no navegador até ser removido explicitamente.
