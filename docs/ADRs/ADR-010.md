# Contrato de comunicação com a API Java

- Status: proposto
- Decisores: Leonardo, Gabrielle, Karen, Antonio
- Data: 2026-09-16
- História Técnica: ADR-010 da planilha "SAUF - ADRs" do frontend web (Vite + React SPA); depende de alinhamento formal com o time de backend

## Contexto e Declaração do Problema

Front e backend (Java) precisam de um contrato estável de comunicação para formato de erros, paginação e datas. Sem isso, cada endpoint tende a inventar seu próprio padrão, quebrando o tratamento centralizado de erros do cliente HTTP (ADR-007). Qual formato adotar para erros, paginação e datas nas respostas da API?

## Fatores da Decisão

- Compatibilidade com o tratamento centralizado de erros do interceptor axios (ADR-007)
- Convenções já nativas do ecossistema Spring (backend em Java)
- Ambiguidade de fuso horário em datas trafegadas entre front e back
- Esforço de alinhamento necessário com o time de backend

## Opções Consideradas

- Contrato padronizado único (erro, paginação e datas definidos uma vez para toda a API)
- Cada endpoint define seu próprio formato conforme a necessidade pontual
- Adotar uma especificação de erro de mercado já pronta (ex.: RFC 7807 - Problem Details) em vez de um formato próprio

## Resultado da Decisão

Opção escolhida: "Contrato padronizado único", porque é a única opção que permite ao front tratar erros, paginação e datas de forma centralizada (ADR-007), sem lógica ad-hoc por endpoint. A decisão fica com status "proposto" até validação formal com o time de backend.

### Consequências Positivas

- Reduz retrabalho de parsing ad-hoc por endpoint no front
- Qualquer desvio do contrato por parte do backend passa a ser tratado como bug de contrato, não como algo a contornar no front
- Facilita a implementação do interceptor de erro único da ADR-007

### Consequências Negativas

- Exige reunião de alinhamento formal com o time de backend Java antes de sair do status "proposto"
- Qualquer mudança futura no contrato precisa ser coordenada entre os dois times, não decidida unilateralmente pelo front

## Prós e Contras das Opções

### Contrato padronizado único

Formato de erro `{ status, error, message, fields }`, paginação no padrão `Pageable` do Spring Data (`page`, `size`, `totalElements`, `totalPages`) e datas em ISO 8601 UTC.

- Bom, porque permite tratamento centralizado de erros no front (ADR-007)
- Bom, porque paginação segue uma convenção já nativa do Spring Data, reduzindo trabalho de adaptação no backend
- Ruim, porque exige esforço de alinhamento e acordo formal entre front e back antes de valer para todos os endpoints

### Cada endpoint define seu próprio formato

Sem padrão único; cada endpoint retorna erros e paginação da forma mais conveniente no momento em que foi criado.

- Bom, porque não exige nenhuma reunião de alinhamento prévia
- Ruim, porque inviabiliza o tratamento centralizado de erros do interceptor axios (ADR-007)
- Ruim, porque gera retrabalho repetido no front a cada novo endpoint com formato diferente

### RFC 7807 (Problem Details)

Adotar a especificação de mercado para formato de erros HTTP, mantendo paginação e datas como decisão à parte.

- Bom, porque é um padrão já documentado e reconhecido, com suporte nativo em algumas bibliotecas Spring
- Bom, porque facilita eventual integração com ferramentas de terceiros que já reconhecem o formato
- Ruim, porque adiciona um padrão externo a mais para o time aprender, sem benefício claro sobre um formato próprio simples para o escopo do SAUF
