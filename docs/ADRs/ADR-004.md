# Estado global de autenticação com Zustand

- Status: proposto
- Decisores: Leonardo, Gabrielle, Karen, Antonio
- Data: 2026-09-16
- História Técnica: ADR-004 da planilha "SAUF - ADRs" do frontend web (Vite + React SPA)

## Contexto e Declaração do Problema

Diversas partes do SAUF precisam saber, a qualquer momento, se há um usuário logado, quem é ele e se sua assinatura está ativa (usado pelos guards de rota da ADR-006, ex.: "simulados exige assinatura"). Onde esse estado deve viver e com qual ferramenta gerenciá-lo?

## Fatores da Decisão

- Quantidade de boilerplate necessária para um estado relativamente pequeno
- Capacidade de evitar re-renders desnecessários em componentes que só leem parte do estado
- Facilidade de testar e mockar o estado
- Curva de aprendizado para o time

## Opções Consideradas

- Zustand
- Redux Toolkit
- Context API pura (React)

## Resultado da Decisão

Opção escolhida: "Zustand", porque atende ao estado de autenticação com API mínima e sem boilerplate, permite seletores granulares que evitam re-renders desnecessários, e é mais simples de testar do que Redux para um estado deste tamanho.

### Consequências Positivas

- API mínima, curva de aprendizado baixa para o time
- Seletores granulares evitam re-render de componentes que não usam o dado alterado
- Middleware de persistência pronto, caso seja necessário persistir algum dado não sensível

### Consequências Negativas

- Adiciona uma dependência de estado global além do React Query (que já cuida do estado de servidor)
- Exige atenção do time para não persistir dados sensíveis de sessão neste store (o token fica em cookie httpOnly, conforme ADR-005)

## Prós e Contras das Opções

### Zustand

Store global leve guardando `user`, `isAuthenticated` e `assinaturaAtiva`, consumido via hooks com seletores.

- Bom, porque tem API mínima e pouquíssimo boilerplate
- Bom, porque permite seletores granulares, evitando re-renders desnecessários
- Ruim, porque é mais uma dependência de gerenciamento de estado no projeto, além do React Query

### Redux Toolkit

Store centralizado com slices, reducers e actions explícitas.

- Bom, porque tem devtools maduro e é bem conhecido no mercado
- Ruim, porque o boilerplate (actions, reducers, slices) é desproporcional para um estado tão pequeno quanto o de sessão
- Ruim, porque aumentaria a curva de aprendizado sem ganho evidente para este caso de uso

### Context API pura

Contexto React nativo, sem biblioteca externa, expondo `user` e funções de login/logout.

- Bom, porque não adiciona nenhuma dependência externa
- Ruim, porque qualquer mudança no contexto re-renderiza todos os componentes que o consomem, sem seletores nativos
- Ruim, porque não tem persistência nem devtools prontos, exigindo implementação manual
