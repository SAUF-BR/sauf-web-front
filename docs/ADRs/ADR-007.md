# Cliente HTTP centralizado com axios e interceptors

- Status: Aceito
- Decisores: Karen
- Data: 2026-09-18
- História Técnica: ADR-007 da planilha "SAUF - ADRs" 

## Contexto e Declaração do Problema

Praticamente todas as features do SAUF fazem chamadas à API Java. Sem padronização, cada uma reimplementaria sua própria lógica de headers, tratamento de erro e redirecionamento em caso de sessão expirada. Como centralizar essa comunicação de forma consistente?

## Fatores da Decisão

- **Manutenibilidade:** Concentrar a URL base, timeout e headers padrão em um único local evita retrabalho caso o endpoint do backend seja alterado.
- **Tratamento Global de Erros:** Necessidade de interceptar respostas com falha (ex: expiração de sessão ou erros de servidor) de forma centralizada em vez de replicar blocos `try/catch` em todas as telas.
- **Padronização de Interceptadores (Interceptors):** Facilidade para injetar tokens de autenticação ou credenciais automaticamente nas requisições de rotas protegidas (como simulados e perfil).
- **Experiência do Desenvolvedor:** Simplificar o código nas camadas de serviços/componentes do React Query, permitindo chamadas mais limpas e tipadas.

## Opções Consideradas

- Instância única de axios com interceptors
- `fetch` nativo espalhado pelo código, chamado diretamente por cada feature
- Camada de abstração própria sobre `fetch` (wrapper customizado sem biblioteca externa)

## Resultado da Decisão

Opção escolhida: "Instância única de axios com interceptors", porque concentra em um só lugar o tratamento de erros, headers e credenciais, evitando duplicação de lógica em cada feature e facilitando ajustes futuros no contrato com o backend (ADR-010).

### Consequências Positivas

- Qualquer mudança no contrato de erro do backend (ADR-010) é ajustada em um único lugar.
- Facilita testes, já que é possível mockar a instância única do cliente HTTP.
- Headers e credenciais (`withCredentials`, necessário para o cookie httpOnly da ADR-005) ficam configurados uma única vez.

### Consequências Negativas

- Introduz uma dependência direta ao axios como parte da arquitetura do front.
- Times acostumados apenas com `fetch` nativo precisam aprender a API do axios e dos interceptors.

## Prós e Contras das Opções

### Instância única de axios com interceptors

Uma instância central (`src/lib/api.ts`) com `baseURL` via variável de ambiente, interceptor de request para headers comuns e interceptor de response para tratamento centralizado de erros.

- Bom, porque interceptors nativos cobrem tratamento de erro e headers sem código repetido.
- Bom, porque é amplamente usado no mercado, com boa documentação.
- Ruim, porque adiciona uma dependência externa ao projeto.

### `fetch` nativo espalhado pelo código

Cada feature chama `fetch` diretamente, implementando sua própria lógica de headers e tratamento de erro.

- Bom, porque não depende de nenhuma biblioteca externa.
- Ruim, porque duplica lógica de erro e headers em cada chamada, aumentando a chance de inconsistência.
- Ruim, porque não tem interceptors nativos, exigindo reimplementar esse conceito manualmente.

### Camada de abstração própria sobre `fetch`

Um wrapper customizado escrito pelo time, imitando o comportamento de interceptors do axios sem usar a biblioteca.

- Bom, porque evita a dependência externa mantendo os mesmos benefícios de centralização.
- Ruim, porque exige manter e testar código próprio que o axios já resolve de forma madura.
- Ruim, porque aumenta o esforço de manutenção sem ganho evidente frente a usar uma biblioteca consolidada.
