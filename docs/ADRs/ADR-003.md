# ADR-003 - React Query para estado de servidor

- Status: aceito
- Decisores: Carlos Eduardo Souza Favarão
- Data: 2026-09-16

## Contexto e Declaração do Problema

Gerenciar cache e estados de requisições ao backend é um desafio recorrente no frontend: estados de loading, erro e sucesso exigem várias linhas de código e diversos `useState` para armazenar e atualizar cada um deles. O React Query (TanStack Query) unifica esses estados e ainda cuida do cache da aplicação de maneira simples e eficiente.

Como gerenciar o estado de servidor (loading, erro, dados e cache) no frontend do projeto da Escola de TI sem espalhar código repetitivo pelos componentes?

## Fatores da Decisão

- Manutenção ativa: biblioteca atualizada constantemente; mesmo já estando em um estágio de desenvolvimento maduro e avançado, continua bem ativa atualmente;
- Simplicidade de aplicação e leitura de código: elimina os diversos estados e atualizações de estados em `try/catch` espalhados pelo frontend;
- Bom gerenciamento de cache: evita requisições em excesso ao backend.

## Opções Consideradas

- Opção 1: Utilizar o React Query (TanStack Query) para gerenciamento de estados e cache
- Opção 2: Gerenciar com `useState()` e `try/catch` nativo

## Resultado da Decisão

Opção escolhida: "Opção 1 - Utilizar o React Query (TanStack Query)", porque atende aos três fatores da decisão: é uma biblioteca mantida ativamente, simplifica o código ao concentrar loading, erro e dados em um único hook e oferece gerenciamento de cache pronto para uso, reduzindo requisições desnecessárias ao backend. O custo de adicionar uma dependência externa é compensado pelo ganho de legibilidade e manutenção.

### Consequências Positivas

- Redução de código repetitivo: não é mais necessário criar múltiplos `useState` e blocos `try/catch` para cada requisição;
- Estados de loading e erro padronizados e fáceis de identificar em toda a aplicação, sem ambiguidade sobre onde um `isLoading` é `true`;
- Menos requisições ao backend graças ao cache gerenciado pela biblioteca;
- Código dos componentes mais limpo e mais fácil de ler e manter.

### Consequências Negativas

- Adição de uma dependência externa ao projeto, que precisa ser mantida e atualizada;
- Curva de aprendizado para quem não conhece conceitos como `queryKey`, `staleTime` e invalidação de cache;
- Configuração de cache inadequada pode exibir dados desatualizados, exigindo definir a estratégia de invalidação (ex.: após mutações);
- Requisições passam a seguir o padrão do React Query, o que deve ser respeitado por toda a equipe para manter a consistência.

## Prós e Contras das Opções

### Opção 1 - React Query (TanStack Query)

Biblioteca para busca, cache, sincronização e atualização de estado de servidor em aplicações React, que fornece hooks como `useQuery` e `useMutation`.

- Bom, porque unifica os estados de loading, erro e dados em um único hook;
- Bom, porque gerencia o cache de forma simples e eficiente, evitando requisições em excesso ao backend;
- Bom, porque é uma biblioteca ativa e constantemente atualizada;
- Bom, porque melhora a legibilidade do código ao eliminar `try/catch` e estados espalhados pelo frontend;
- Ruim, porque exige o uso de uma biblioteca externa no projeto.

### Opção 2 - `useState()` e `try/catch` nativo

Gerenciamento manual dos estados de requisição usando apenas recursos nativos da stack da aplicação (React e TypeScript).

- Bom, porque não exige nenhuma biblioteca externa;
- Bom, porque utiliza apenas funções nativas da stack já adotada (React e TypeScript);
- Ruim, porque é verbosa: cada requisição demanda vários estados e blocos `try/catch`;
- Ruim, porque é difícil de gerenciar e pode causar confusão na hora de definir o que e onde um `isLoading` é `true`;
- Ruim, porque o cache precisaria ser implementado manualmente, ou simplesmente não existiria.
