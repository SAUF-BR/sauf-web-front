# Organização de pastas por feature (domínio) em vez de por tipo de arquivo

- Status: Aceito
- Decisores: Leonardo, Gabrielle, Karen, Antonio
- Data: 2026-09-16
- História Técnica: ADR-002 da planilha "SAUF - ADRs".

## Contexto e Declaração do Problema

Um dos desafios durante o desenvolvimento de um sistema é manter os arquivos de código organizados conforme o projeto cresce. Quando não existe um padrão definido desde o início, a estrutura de pastas tende a ser criada conforme novas funcionalidades são desenvolvidas, podendo resultar em arquivos espalhados e dificultar a localização, compreensão e manutenção do código.

Para evitar esse problema no SAUF BR, é necessário definir um padrão para a organização dos arquivos do frontend. Para isso, optamos pela organização de pastas por feature/domínio.

## Fatores da Decisão

- Facilidade para localizar arquivos relacionados a uma mesma funcionalidade;
- Baixo acoplamento entre módulos diferentes;
- Facilidade de manutenção e evolução do código;
- Facilidade para o trabalho paralelo entre os integrantes da equipe;
- Redução de conflitos de merge entre pessoas trabalhando em features diferentes.

## Opções Consideradas

- Organização por feature/domínio (`src/features/<dominio>/...`)
- Organização por tipo de arquivo (`src/components/`, `src/hooks/`, `src/services/` globais)
- Estrutura híbrida (por tipo no topo, com subpastas por domínio dentro de cada tipo)

## Resultado da Decisão

Opção escolhida: **Organização por feature/domínio**.

Escolhemos essa opção porque ela mantém os arquivos relacionados a uma mesma funcionalidade agrupados em um único local, incluindo componentes, hooks, serviços de API, estilos e outros arquivos específicos daquela feature. Essa organização facilita a localização dos arquivos, reduz o acoplamento entre diferentes módulos e favorece o trabalho paralelo de múltiplas pessoas.

### Consequências Positivas

- Maior facilidade para localizar e entender tudo relacionado a uma funcionalidade do sistema;
- Melhor separação das responsabilidades entre os diferentes módulos;
- Maior facilidade de manutenção e evolução das funcionalidades;
- Menos conflitos de merge entre pessoas trabalhando em features diferentes;
- Facilita o trabalho paralelo da equipe.

### Consequências Negativas

- Pode haver duplicação de pequenos componentes entre features;
- Exige disciplina da equipe para identificar quando um recurso deve permanecer específico de uma feature ou se tornar compartilhado;
- Pode exigir reorganização de arquivos quando um componente inicialmente específico passa a ser utilizado por várias features.

## Prós e Contras das Opções

### Organização por feature/domínio

Cada funcionalidade ou módulo de negócio terá sua própria pasta contendo seus componentes, hooks, serviços, schemas e demais arquivos relacionados. Recursos utilizados por múltiplas features serão mantidos em uma pasta compartilhada.

- Bom, porque tudo relacionado a uma funcionalidade fica concentrado em um único local;
- Bom, porque facilita a localização e manutenção dos arquivos;
- Bom, porque reduz o acoplamento entre módulos diferentes;
- Bom, porque facilita o desenvolvimento paralelo pela equipe;
- Ruim, porque pode ocorrer uma pequena duplicação de código antes de ser identificada a necessidade de compartilhamento de determinado recurso.

### Organização por tipo de arquivo

Todos os componentes ficam em `components/`, todos os hooks em `hooks/`, todos os serviços em `services/`, independentemente da funcionalidade ou módulo de negócio ao qual pertencem.

- Bom, porque é uma estrutura simples e fácil de configurar no início do projeto;
- Bom, porque deixa claro onde encontrar determinado tipo de arquivo;
- Ruim, porque, conforme o projeto cresce, os arquivos relacionados a uma única funcionalidade ficam espalhados entre diferentes pastas;
- Ruim, porque dificulta visualizar rapidamente todos os arquivos envolvidos em uma funcionalidade;
- Ruim, porque pode aumentar o acoplamento entre módulos sem fronteiras bem definidas.

### Estrutura híbrida

Mantém pastas por tipo no nível raiz, mas utiliza subpastas organizadas por domínio dentro de cada uma (ex.: `components/cursos/`, `hooks/cursos/`, `services/cursos/`).

- Bom, porque preserva a familiaridade da organização por tipo;
- Bom, porque ainda permite alguma separação entre os diferentes domínios;
- Ruim, porque exige navegar entre várias pastas para encontrar todos os arquivos relacionados a uma única funcionalidade;
- Ruim, porque não concentra a feature em um único local;
- Ruim, porque não resolve o problema de navegação de forma tão direta quanto a organização por feature.
