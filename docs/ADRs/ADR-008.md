# ADR-008 - Validação de formulários (React Hook Form + Zod)

- Status: aceito
- Decisores: Heloísa Tognólli Scarante
- Data: 2026-09-18

## Contexto e Declaração do Problema

O frontend da Escola de TI possui vários formulários que precisam validar os dados do usuário antes de enviá-los ao backend: **login**, **cadastro**, **configuração de simulado** e **perfil**. Validar cada formulário à mão, com um `useState` por campo e regras escritas dentro dos componentes, gera código repetitivo, mensagens de erro inconsistentes e regras difíceis de reaproveitar entre telas.

Como validar os dados dos formulários do frontend de forma consistente, tipada e sem repetir código em cada tela?

## Fatores da Decisão

- Simplicidade e menos código repetitivo: evitar um `useState` e um bloco de validação para cada campo de cada formulário;
- Regras em um único lugar: as regras de validação devem ficar declaradas em schemas reaproveitáveis, e não misturadas ao JSX dos componentes;
- Tipagem com TypeScript: os tipos dos dados do formulário devem vir das próprias regras de validação, evitando duplicar tipos e regras;
- Experiência do usuário: mensagens de erro claras e consistentes, exibidas por campo, sem renderizações desnecessárias a cada tecla digitada;
- Consistência com a stack: a solução deve funcionar bem com a SPA em React e TypeScript ([ADR-001](ADR-001.md)) e com o envio dos dados por meio do React Query ([ADR-003](ADR-003.md)).

## Opções Consideradas

- Opção 1: React Hook Form com Zod (via `zodResolver`)
- Opção 2: Validação manual com `useState()` e funções próprias
- Opção 3: Formik com Yup

## Resultado da Decisão

Opção escolhida: "Opção 1 - React Hook Form + Zod", porque o React Hook Form cuida do estado do formulário (valores, erros, campos alterados e envio) com poucas linhas de código e poucas renderizações, e o Zod permite declarar as regras de validação em schemas reaproveitáveis dos quais o TypeScript infere os tipos (`z.infer`). Juntos, eliminam o código repetitivo de validação e mantêm regras e tipos sincronizados.

### Detalhes da implementação

- **Schemas:** cada formulário (login, cadastro, configuração de simulado e perfil) possui um schema Zod próprio, e o tipo dos dados vem de `z.infer<typeof schema>`. Regras compartilhadas entre telas, como e-mail e senha, ficam em schemas reaproveitáveis.
- **Integração:** o `useForm` recebe o schema por meio do `zodResolver` (pacote `@hookform/resolvers`), e as mensagens de erro são exibidas por campo.
- **Regras entre campos:** validações que dependem de mais de um campo, como a confirmação de senha no cadastro, usam `refine` ou `superRefine` do Zod.
- **Envio:** o envio dos dados ao backend é feito com `useMutation` do React Query ([ADR-003](ADR-003.md)), e erros de validação retornados pelo backend são mapeados para os campos com `setError`.
- **Backend:** a validação no frontend melhora a experiência do usuário, mas não substitui a validação do backend, que continua validando todos os dados recebidos (ex.: Bean Validation no Spring Boot).

### Consequências Positivas

- Regras de validação declarativas, reaproveitáveis e separadas dos componentes;
- Tipos do TypeScript inferidos dos schemas, sem duplicar regras e tipos;
- Menos código nos formulários: sem `useState` por campo e sem `try/catch` de validação espalhados;
- Mensagens de erro consistentes em todos os formulários;
- Bom desempenho: o React Hook Form usa campos não controlados por padrão e evita renderizar o formulário inteiro a cada tecla digitada.

### Consequências Negativas

- Adição de duas dependências externas ao projeto (React Hook Form e Zod), além do pacote de integração `@hookform/resolvers`, que precisam ser mantidas e atualizadas;
- Curva de aprendizado para quem não conhece conceitos como `register`, `Controller`, `zodResolver` e `refine`;
- Componentes de UI controlados (ex.: selects e campos personalizados) exigem o `Controller` ou `useController`, o que é menos direto que o `register`;
- As regras do schema no frontend podem divergir das regras do backend, exigindo cuidado para mantê-las alinhadas.

## Prós e Contras das Opções

### Opção 1 - React Hook Form + Zod

React Hook Form para gerenciar o estado e o envio dos formulários, e Zod para declarar os schemas de validação com inferência de tipos, integrados pelo `zodResolver`.

- Bom, porque reduz o código repetitivo de estado e validação de cada formulário;
- Bom, porque os schemas concentram as regras em um único lugar e geram os tipos do TypeScript;
- Bom, porque tem bom desempenho, com poucas renderizações;
- Bom, porque é amplamente usado no ecossistema React, com ampla documentação;
- Ruim, porque exige bibliotecas externas e uma curva de aprendizado inicial;
- Ruim, porque campos controlados exigem `Controller`.

### Opção 2 - Validação manual com `useState()` e funções próprias

Cada formulário guarda valores e erros em `useState` e valida os dados com funções escritas à mão.

- Bom, porque não exige nenhuma biblioteca externa;
- Bom, porque usa apenas recursos nativos da stack (React e TypeScript);
- Ruim, porque é verbosa: cada campo demanda estado, validação e mensagem de erro;
- Ruim, porque as regras se repetem entre telas e ficam inconsistentes;
- Ruim, porque os tipos e as regras precisam ser mantidos separadamente;
- Ruim, porque atualizar o estado a cada tecla digitada pode causar renderizações desnecessárias.

### Opção 3 - Formik com Yup

Formik para gerenciar o estado dos formulários, e Yup para declarar os schemas de validação.

- Bom, porque é uma combinação conhecida e consolidada no ecossistema React;
- Bom, porque separa as regras de validação em schemas;
- Ruim, porque o Formik renderiza o formulário com mais frequência e tende a ter desempenho inferior;
- Ruim, porque o Yup tem inferência de tipos com TypeScript menos direta que o Zod;
- Ruim, porque exige mais código para montar cada formulário.
