# Avaliação do Tailwind CSS para estilização

- Status: rejeitado
- Decisores: Leonardo
- Data: 2026-09-16
- História Técnica: ADR-011 — avaliação de uma abordagem alternativa de estilização (utility-first), em complemento à decisão da ADR-009

## Contexto e Declaração do Problema

Além do CSS Modules, decidido na ADR-009, o time avaliou também adotar o Tailwind CSS como abordagem de estilização para o SPA do SAUF, considerando os ganhos de produtividade e consistência de design que soluções utility-first costumam oferecer. Vale a pena adotar o Tailwind CSS, mesmo com o time já tendo optado por CSS Modules na ADR-009?

## Fatores da Decisão

- Esforço de aprendizado das classes utilitárias e da configuração do Tailwind
- Prazo do projeto acadêmico, que não comporta uma curva de aprendizado longa
- Familiaridade do time já consolidada com CSS tradicional (ADR-009)
- Ganho de produtividade prometido pelo Tailwind frente ao esforço necessário para obtê-lo

## Opções Consideradas

- Adotar o Tailwind CSS
- Não adotar, mantendo apenas CSS Modules (ADR-009)

## Resultado da Decisão

Opção escolhida: "Não adotar, mantendo apenas CSS Modules", porque o time verificou, na prática, que o esforço de aprender e configurar corretamente o Tailwind CSS seria muito maior do que simplesmente utilizar o CSS Modules, com o qual o time já tem familiaridade e tempo hábil suficiente no cronograma do projeto.

### Consequências Positivas

- Evita gastar tempo do cronograma aprendendo uma ferramenta nova sem necessidade
- Mantém uma única abordagem de estilização no projeto (CSS Modules), reduzindo inconsistência

### Consequências Negativas

- O time abre mão da centralização de tokens de design em um único arquivo de configuração, que o Tailwind ofereceria
- Abre mão também da produtividade de prototipagem rápida por classes utilitárias prontas

## Prós e Contras das Opções

### Adotar o Tailwind CSS

Abordagem utility-first, com classes aplicadas diretamente no JSX e configuração central de design tokens.

- Bom, porque tem custo zero em runtime (compilado em build)
- Bom, porque centraliza tokens de design em um único arquivo de configuração
- Ruim, porque o esforço de aprendizado se mostrou muito maior do que o previsto, incompatível com o prazo do projeto

### Não adotar (manter CSS Modules da ADR-009)

Seguir apenas com a abordagem já decidida na ADR-009.

- Bom, porque não exige nenhum esforço adicional de aprendizado além do que o time já domina
- Bom, porque mantém uma única abordagem de estilização em todo o projeto
- Ruim, porque perde os ganhos de produtividade e consistência de tokens que o Tailwind ofereceria
